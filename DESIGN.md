## 1. Design principles

The design follows the shadcn/ui philosophy, not a component-library dependency.

### 1.1 Open code, not a black box

Components are **source code in this repository** — generated by the shadcn CLI when a
registry component is used, or authored in the same style into `src/components/ui/`. We can
read, diff, patch, and delete them. We do not install a runtime UI package that hides markup,
styles, or accessibility behavior.

Consequences:

- Every component is reviewable in a pull request.
- A local patch is allowed, but it must be recorded in the component's patch note and
  covered by a test or a visual check.
- Upstream updates arrive through the registry/CLI as diffs, never as an invisible
  transitive upgrade.

### 1.2 Composition over configuration

We install primitives (button, dialog, field, table, sidebar) and **compose** them in
feature components. We do not build a parallel "MegaTable" or "SuperForm" layer that
re-implements the primitives behind dozens of boolean props.

- Shared composition belongs in `src/components/common/`.
- Feature-specific composition belongs in `src/features/<feature>/components/`.
- If a component needs more than ~8 props or two rendering modes, split it.

### 1.3 Semantic tokens only

Color, radius, and typography are consumed through CSS variables and Tailwind utilities:
`bg-background`, `text-muted-foreground`, `border-border`, `ring-ring`.
Raw hex values, arbitrary RGB/OKLCH values, and one-off shadows are prohibited in
feature code. A color change must be a token change with a contrast check.

### 1.4 Accessible primitives, accessible composition

shadcn primitives sit on accessible headless primitives (Radix/Base UI, depending on the
CLI output). We inherit that behavior and must not break it: labels, focus management,
escape/outside-click, roving tab index, and screen-reader announcements.

### 1.5 Own the surface, keep the system small

The console should feel like one product, not a gallery of components. Use a small,
opinionated set:

- one page header pattern
- one table pattern
- one form-section pattern
- one confirmation dialog pattern
- one empty/loading/error pattern
- one status-badge vocabulary

New patterns require a design note in this file.

### 1.6 Operational honesty

This is a console for money and production routing. The UI must show:

- what will change (before → after)
- who is acting (session identity → `X-Admin-Actor`)
- when it changed (revision, timestamp, audit)
- what actually happened (success, failure, request ID)
- when data is stale or unavailable

No fake dashboards, no invented metrics, no optimistic money mutations, no hidden
destructive defaults.

## 2. Product direction

**Calm control room.** Dense enough for operators, quiet enough to scan under pressure.

- Flat surfaces, 1px borders, no drop shadows. The supplied theme deliberately sets
  shadow opacity to zero; keep it that way.
- Orange is the signal color: one primary action per view. It is not a success color and
  not a large background wash.
- Blue is informational and navigational: selection, links, focus, sidebar active state.
- Green/amber/red are reserved for status and outcome, always paired with a label or icon.
- Generous page margins, compact table rows, monospace for IDs, tabular numerals for money
  and token counts.
- No marketing hero, no decorative gradients, no glassmorphism, no stock illustrations.

## 3. Theme provenance and token contract

The palette comes from the tweakcn registry item:

~~~text
https://tweakcn.com/r/themes/cmthn09qj000004jx7ky299wm
~~~

The theme is a shadcn `registry:style` item with light and dark CSS variables. It uses
**Open Sans**, an orange primary (`oklch(0.7080 0.1915 45.8767)`), a blue accent, pure
white/black surfaces, and flat shadows.

### 3.1 Intentional deviations from the raw theme

The raw theme is the color authority. Three categories are intentionally adjusted, and
only these:

| Area | Raw theme | Committed value | Why |
|---|---|---|---|
| Primary foreground | White (2.78:1 on orange) | Dark foreground (6.66:1) | White text on the orange fails WCAG AA for normal text |
| Accent/ring/sidebar blue | Bright blue (2.46–2.83:1 in places) | Darker blue (`oklch(0.55 0.17 250)`) | Meets 3:1 UI and 4.5:1 text contrast |
| Radius | `1.3rem` (20.8px) | `0.75rem` (12px) | A 20.8px radius is a marketing signature; it reduces density and makes tables/forms feel bubbly. Color and type stay faithful; geometry is tuned for an operator console. |

Additional accessibility repair: light `muted-foreground`, light `destructive`,
dark `destructive`, light/dark `input`, and dark `muted-foreground` are adjusted to pass
contrast. These are listed in §6. Do not "restore" a raw token without re-running the
contrast check.

### 3.3 Token usage map

| Token | Use |
|---|---|
| `background` / `foreground` | App canvas and primary text |
| `card` / `card-foreground` | Panels, tables, dialogs on light surfaces |
| `primary` / `primary-foreground` | One primary action per view; active emphasis; brand signal |
| `secondary` / `secondary-foreground` | High-emphasis neutral action; inverted chips |
| `muted` / `muted-foreground` | Metadata, disabled surfaces, table headers |
| `accent` / `accent-foreground` | Hover, selected row, inline links, informational emphasis |
| `destructive` / `destructive-foreground` | Destructive actions and error emphasis |
| `border` | Decorative separators and card edges |
| `input` | Form control boundaries (must remain ≥3:1) |
| `ring` | Focus ring and selected control outline |
| `success`, `warning`, `info` | Status surfaces and badges, with matching foreground |
| `brand-panel` / `brand-panel-foreground` | The permanently dark login/operator panel; not a general card surface |
| `chart-*` | Data visualization only; never decorative |

**Orange is never body text on white.** It is a surface color with dark foreground, or a
large graphical accent. It is not a success color.

The login split panel uses the four `brand-panel` tokens. They stay dark in both themes and
are the only place where a permanently dark surface is allowed; do not reuse them for cards,
dialogs, or data panels.

## 4. Typography

- Family: **Open Sans** for UI; **Menlo** for IDs, JSON, tokens, and code.
- Self-host Open Sans through `@fontsource-variable/open-sans` (or the current
  `@fontsource` package) so the app does not depend on Google Fonts at runtime and the CSP
  can stay strict.
- Base size: 14px (`text-sm`) for controls and tables; 16px for prose/help pages.
- Weights: 400 body, 500 labels/emphasis, 600 headings, 700 reserved for page titles.
- Numbers: `font-variant-numeric: tabular-nums` on all money, token, duration, revision,
  and timestamp columns.
- Line length: 60–75 characters for prose; tables may exceed.

| Role | Size / line height | Weight | Usage |
|---|---|---|---|
| Display | 30 / 36 | 700 | Login and rare empty-page moments |
| Page title | 24 / 32 | 600 | One per route |
| Section title | 18 / 28 | 600 | Card/dialog sections |
| Body | 14 / 20 | 400 | Default |
| Body strong | 14 / 20 | 600 | Labels, key values |
| Small | 12 / 16 | 400 | Metadata, help text, table footers |
| Mono | 12 / 18 | 400 | IDs, JSON, tokens |
| Overline | 11 / 16 | 600, uppercase, tracking-wide | Rare group labels |

Avoid all-caps sentences. Overline is only for compact group labels.

## 5. Spacing, radius, elevation, layout

### 5.1 Spacing

4px base. Use the standard Tailwind scale; do not invent pixel values.

| Context | Value |
|---|---|
| Page padding | 24px desktop, 16px tablet/mobile |
| Section gap | 32px |
| Card padding | 20px (compact) / 24px (standard) |
| Form field gap | 20px |
| Table row height | 44px compact / 48px standard |
| Button height | 32px small / 36px default / 40px large |
| Toolbar gap | 8px |
| Badge height | 20px |

### 5.2 Radius

Committed `--radius: 0.75rem` (12px). Derived: sm 8px, md 10px, lg 12px, xl 16px.

- Cards, dialogs, sheets: `rounded-xl` (16px) or `rounded-lg`.
- Buttons/inputs: `rounded-md` (10px).
- Badges: `rounded-full` for status, `rounded-md` for metadata chips.
- Tables: square outer corners inside cards; no per-cell rounding.

### 5.3 Elevation

The theme's shadows are transparent. **Do not add drop shadows.** Use:

- 1px border
- surface color contrast
- overlay scrim (`bg-black/50`) for modal layers
- a single inset ring for focused/dirty states

This keeps the interface legible on low-quality monitors and avoids the generic SaaS
"floating card" look.

### 5.4 Layout

- App shell: left sidebar 248px (collapsible to 64px), top bar 56px, content max-width
  1440px, centered with page padding.
- Detail pages: two columns at ≥1280px (main 2/3, context/audit 1/3); stacked below.
- Tables: full width of the content area; horizontal scroll only when necessary; sticky
  header and sticky first column for very wide usage/ledger tables.
- Forms: single column, max 720px; JSON/config editors can expand to 960px.
- Never hide primary navigation behind a hamburger on desktop; collapse to icons first.
- On mobile, sidebar becomes a sheet; tables become horizontally scrollable, not cards
  with duplicated fields.

## 6. Contrast and accessibility ledger

Computed with the WCAG 2.x relative-luminance formula against the committed tokens.

| Pair | Ratio | Requirement | Result |
|---|---|---|---|
| foreground / background (light) | 18.51:1 | 4.5:1 text | Pass |
| muted-foreground / background (light) | ~7.1:1 | 4.5:1 | Pass |
| primary-foreground / primary | 6.66:1 | 4.5:1 | Pass (override) |
| accent-foreground / accent (light) | 4.97:1 | 4.5:1 | Pass (override) |
| input / background (light) | 3.35:1 | 3:1 UI | Pass (override) |
| ring / background (light) | ~4.8:1 | 3:1 UI | Pass (override) |
| destructive / background | 4.79:1 | 4.5:1 | Pass (override) |
| white / destructive | 4.79:1 | 4.5:1 | Pass (override) |
| foreground / background (dark) | 17.24:1 | 4.5:1 | Pass |
| muted-foreground / card (dark) | 4.88:1 | 4.5:1 | Pass (override) |
| primary-foreground / primary (dark) | 6.66:1 | 4.5:1 | Pass (override) |
| white / sidebar-primary | ~4.8:1 | 4.5:1 | Pass (override) |

Notes:

- The raw theme's white-on-orange was **2.78:1** and its bright blue accent was as low as
  **2.46:1**. Those combinations are prohibited.
- `chart-3` (yellow) and `chart-1` (light blue) are not safe as small text on white.
  Charts must use labels, legends, and patterns; never rely on hue alone.
- `border` is decorative; `input` is the accessible form boundary.
- Status badges pair color with a text label and, where useful, an icon. Color alone never
  communicates enabled/disabled/error.

### 6.1 Keyboard and focus

- Every interactive element is reachable by Tab in DOM order.
- Focus ring: 2px `ring-ring` with 2px offset on the surface; never remove it.
- Dialogs/sheets trap focus, restore it on close, and close on Escape unless a request is
  in flight (then show a pending state instead of silently ignoring Escape).
- Tables support arrow-key row navigation only if it does not conflict with native
  scrolling; row actions are always reachable by Tab.
- Skip link to `#main`.
- Toasts are announced via `aria-live="polite"`; errors via `role="alert"`.
- Respect `prefers-reduced-motion`; no animation is required to understand state.

### 6.2 Target size and forms

- Minimum target 24×24px, preferred 36×36px.
- Labels are always visible; placeholders are examples, never labels.
- Errors are inline, associated with `aria-describedby`, and summarized at the top of the
  form on submit.
- Required fields are marked in text, not only with an asterisk color.

## 7. Component rules

### 7.1 Buttons

| Variant | Use | Rule |
|---|---|---|
| `default` | The single primary action on a page/dialog | Orange surface, dark text |
| `secondary` | High-emphasis neutral (e.g. "Save draft") | Dark surface in light mode; use sparingly |
| `outline` | Secondary actions, row actions | 1px input/border; no shadow |
| `ghost` | Tertiary actions, icon buttons | Hover uses accent |
| `destructive` | Kill switch, revoke, destructive confirm | Red surface, white text |
| `link` | Inline navigation | Blue accent, underline on hover/focus |

Rules: one primary button per view; icon-only buttons require `aria-label` and a tooltip;
pending buttons keep their width and show a spinner plus a verb ("Saving…"); destructive
buttons never sit next to the primary action without spacing and a confirmation.

### 7.2 Forms

- Sectioned card: **Identity**, **Commercial**, **Capabilities**, **Limits**, **Fair use**,
  **App gating**. Only sections that apply to the capability kind are shown.
- Sticky footer with **Cancel**, **Review changes**, and a dirty indicator.
- Review step shows a before/after diff of changed fields, the actor, and the capability
  revision. Confirming sends the full PUT body.
- JSON fields (`limits`, `fair_use`, provider `config`) use a monospace editor with
  client-side JSON validation and a "Format" action. Never submit invalid JSON.
- Numbers are integers where the backend expects integers. Do not coerce `cost_credits`
  or `cost_per` through floating point.
- Unknown/extra fields from the API are preserved when editing, not silently dropped.

### 7.3 Tables

- Use TanStack Table + shadcn table primitives.
- Header: muted background, 12px uppercase label optional, sort indicator.
- Rows: 44–48px, 1px divider, hover `accent/40`.
- Numeric columns right-aligned with tabular numerals.
- IDs are monospace, truncated in the cell with a copy button and full value in a tooltip.
- Status is a badge with label; disabled is not just a gray row.
- Row actions in a dropdown at the end; the primary row action is a link, not a hidden menu.
- Empty state replaces the body, not the header.
- Loading uses skeleton rows matching the final column widths.
- Pagination is cursor-based: **Newer / Older**, showing the current range when known; no
  page-number fiction.
- Column visibility is optional; no drag-to-reorder in v1.

### 7.4 Dialogs and confirmations

Use an `AlertDialog` for destructive/high-impact actions, a `Dialog` for forms, and a
`Sheet` for contextual detail on narrow screens.

High-impact actions require:

1. A one-sentence description of the production impact.
2. A before → after summary.
3. A reason field (kill switch, grant) where the API requires or the audit benefits.
4. Explicit confirmation button labeled with the action ("Disable capability", "Grant 50
   credits"), not "OK".
5. For disabling a capability, type the capability ID to confirm.

### 7.5 Status vocabulary

| Status | Token | Label examples |
|---|---|---|
| Enabled / healthy / committed | `success` | Enabled, Committed, OK |
| Disabled / failed / refunded | `destructive` or neutral | Disabled, Failed, Refunded |
| Pending / reserved / warning | `warning` | Reserved, Pending, Degraded |
| Informational / neutral | `info` or `muted` | Unknown, Not configured |

Success and warning badges use solid semantic fills with their matching foreground; tinted
fills were measured below AA at 11px and are not allowed for those two statuses.

Internal ledger states are displayed verbatim in a monospace badge with a tooltip:
`PENDING_SPEND`, `RESERVED`, `COMMITTED`, `REFUND_PENDING`, `REFUNDED`, `EXPIRED`,
`FAILED`. Do not collapse them in the admin UI; operators need the internal state.

### 7.6 JSON and diff viewers

- Read-only JSON is rendered as a tree with collapsible nodes, copy, and raw view.
- Never inject API strings through `dangerouslySetInnerHTML`.
- Diffs show changed keys only by default, with "show unchanged" toggle.
- Red/green is paired with `-/+` markers and labels.

### 7.7 Empty, loading, error

- Empty: icon, short title, one sentence, one action. No illustration.
- Loading: skeleton that matches the layout; a centered spinner is only for short,
  contained actions.
- Error: what failed, what to do, the request ID, and a retry. Never a blank screen.
- Partial data: show what loaded, mark the failed panel, keep the page usable.

### 7.8 Toasts

- Success: short confirmation and the request ID in a "Details" disclosure.
- Error: message + retry where safe; no retry for non-idempotent mutations.
- No toast for field validation; keep it inline.
- Maximum one toast per action; dedupe by request ID.

## 8. Motion

- Duration 120–180ms for hover/focus, 180–240ms for dialogs/sheets.
- Easing: `ease-out` for entrances, `ease-in` for exits.
- Animate opacity and transform only; never animate layout-critical table dimensions.
- No looping decorative animation. Skeleton shimmer is allowed and disabled under
  `prefers-reduced-motion`.
- Page transitions are a subtle fade; data refreshes do not re-mount the page.

---

## 9. Dark mode

- Class strategy: `.dark` on `<html>`; no CSS media-query-only theme.
- Default follows `prefers-color-scheme`; the user can override to light/dark/system.
- Persist in `localStorage` under one key, and apply an inline boot script before paint to
  avoid a flash.
- Dark background is pure black; cards are `#17181c`-equivalent. Borders must remain
  visible; do not use pure black on pure black.
- Test every screen in both modes, including charts, JSON viewers, and disabled states.
- The theme toggle is in the user menu, not the primary navigation.

---

## 10. Content and tone

- Sentence case for labels, buttons, titles, and menu items.
- Verbs for actions: "Save changes", "Disable capability", "Grant credits".
- State the object: "Delete model" is clearer than "Delete".
- Errors say what happened and what to do; no stack traces, no provider payloads.
- Use "credits" in UI copy; "CRD" only in data/columns where the API uses it.
- Use "capability" and "model" consistently; do not alternate with "service" and "agent".
- Timestamps: local time with a UTC tooltip; relative time ("2 min ago") only as secondary.
- Empty copy: "No capabilities match these filters." not "Nothing here yet!".
- No exclamation marks, no jokes, no emoji as UI icons.

---

## 11. Implementation contract

1. `src/components/ui/` is generated by shadcn and owned by this repo. Do not wrap every
   primitive; compose in feature components.
2. `src/components/common/` holds shared compositions: PageHeader, DataTable,
   ConfirmDialog, EmptyState, ErrorState, StatusBadge, JsonViewer, CopyButton, DiffView.
3. `src/features/<feature>/components/` holds feature-specific compositions only.
4. All colors, radii, and fonts come from tokens. `className` may use semantic utilities,
   never `text-[#...]` or `bg-[oklch(...)]`.
5. Use `cn()` from `@/lib/utils` for conditional classes; use CVA for variants.
6. Icons: Lucide, 16px in dense UI, 20px in buttons, `aria-hidden` when decorative.
7. No component library beyond shadcn primitives + the approved stack.
8. New shared components require a usage note and at least one test/visual state.
9. Never ship a component that cannot be keyboard-operated and screen-reader-labeled.
10. Every screen has a loading, empty, error, and (where relevant) permission-denied state.

### 11.1 shadcn installation rules

- Initialize with the current shadcn CLI and Tailwind v4, using `components.json`
  `cssVariables: true`.
- Add only the components used; do not bulk-install the catalog.
- Pin the CLI version in the PR description and commit the generated files, not a
  dependency on the CLI at runtime.
- Treat the tweakcn registry item as a theme source, then commit the resulting CSS. The
  committed CSS is the runtime source of truth; do not fetch a theme at runtime.
- Local patches to generated components are allowed but must be minimal and documented at
  the top of the file with a `PATCH:` comment.

## 12. Design review checklist

Before merging a UI change:

- [ ] Uses only semantic tokens; no raw colors or arbitrary shadows.
- [ ] Light and dark screenshots attached to the PR.
- [ ] Contrast checked for new color pairs (4.5:1 text, 3:1 UI).
- [ ] Keyboard path works end to end; focus visible.
- [ ] Screen reader labels for icon-only controls and status badges.
- [ ] Loading, empty, error, and permission states exist.
- [ ] Primary action is singular and obvious.
- [ ] Destructive action has impact copy and confirmation.
- [ ] Numbers are tabular and right-aligned.
- [ ] No layout shift on load; skeleton matches content.
- [ ] `prefers-reduced-motion` respected.
- [ ] Mobile/narrow viewport checked (sidebar sheet, table scroll).

---

## 13. Governance

- This file is part of the product, not decoration. A design change that alters tokens,
  typography, radius, or a shared pattern updates this file in the same PR.
- Theme upgrades: diff the registry item, update the token block, re-run the contrast
  ledger, and attach before/after screenshots.
- Do not add a second design system, a second icon set, or a second toast library.
- When in doubt, choose the quieter option: fewer colors, fewer borders, more spacing,
  one clear action.
