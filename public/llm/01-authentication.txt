# MemeChat Gateway - Authentication

Parent index: llm.txt
Related: llm/02-request-lifecycle-and-states.txt, llm/09-errors-and-http-status.txt

## 1. App-client authentication

Every /v1 request must include:

  X-App-Client-Key: <40 lowercase hexadecimal characters>

The key is generated by the gateway at app-client creation:

  POST /internal/admin/app-clients

and returned exactly once. The key has 20 random bytes rendered as 40 hex
characters.

The gateway stores only a digest. A database read cannot recover the key.

## 2. What the gateway checks

For a /v1 request:

1. The header must be present when APP_CLIENT_AUTH=required (the live mode).
2. The format must be exactly 40 hexadecimal characters.
3. The digest must resolve to a client row.
4. The client must be enabled.
5. The specific ability must have an enabled route for that client.

Any failure at checks 1-4 returns:

HTTP 401
Content-Type: application/json; charset=utf-8

{
  "code": "UNAUTHENTICATED",
  "message": "missing app client key",
  "requestId": "<gateway request id>"
}

Other 401 messages can be:

- "invalid app client key"
- "unknown or disabled app client"
- "missing app client key"

Do not branch on message text. Branch on HTTP 401 and code UNAUTHENTICATED.

Check 5 is capability-specific:

- chat: 403 CAPABILITY_NOT_IN_PLAN when no llm route exists
- tts/stt/embeddings: 403 CAPABILITY_NOT_IN_PLAN when no route exists;
  503 CAPABILITY_DISABLED when a route exists but its provider is unavailable
- vector: 403 CAPABILITY_NOT_IN_PLAN when no vector route exists
- capabilities manifest: returns only the abilities that are routed; it does
  not fail with 403 merely because an ability is unrouted

## 3. Header format

- Header name: X-App-Client-Key
- Value: 40 hex characters, case-insensitive on input; canonical lowercase.
- Surrounding whitespace is trimmed.
- The header is not accepted in a query string.
- The header is not accepted as a JSON body field.

The app-client key is an application secret. It is not a user token. It is not
a Firebase token. It is not a session cookie.

## 4. Optional Firebase UID header

Apps that use Firebase may send:

  X-Firebase-Uid: <user id>

It is optional per app client. Some app clients have require_firebase_uid=true;
for those, omitting the header returns 401 UNAUTHENTICATED with message
"missing firebase user id".

Validation rules:

- Maximum length 128 characters.
- Must not contain spaces, tabs, carriage returns, or newlines.
- It is attached as request identity metadata.

Important current limitation:

The gateway does not verify a Firebase ID token and does not use the Firebase
Admin SDK. X-Firebase-Uid is not an authentication or authorization boundary
today. Do not use it for billing, ownership, or per-user data isolation until
token verification is added.

## 5. App-client lifecycle states

ACTIVE:
  The key resolves to an enabled client. Requests may proceed.

DISABLED:
  The client row exists but enabled=false. All /v1 requests return 401
  UNAUTHENTICATED ("unknown or disabled app client").

KEY ROTATED:
  The operator rotates the key. The old key stops resolving immediately.
  The new key is returned once and must replace the stored key.

DELETED:
  The client row and its routes are deleted. The key returns 401.

CACHE BEHAVIOR:
  Client lookups are cached in-process and in Redis. Admin mutations invalidate
  the affected digest; other instances may take a short interval to observe a
  rotation or disable.

## 6. Key rotation procedure for clients

1. Operator rotates the key in the backoffice.
2. Operator delivers the new key through a secure channel.
3. App replaces the stored key.
4. App retries requests. Old key receives 401.

Never send the key in a URL, log, crash report, analytics event, or screenshot.

## 7. Authentication errors and client action

HTTP 401 UNAUTHENTICATED
  Missing, malformed, unknown, disabled, or rotated key; or missing required
  Firebase UID.
  Action: fix the key/header. Do not retry with the same credentials.

HTTP 403 CAPABILITY_NOT_IN_PLAN
  The key is valid, but this app client has no route for the requested ability.
  Action: operator must assign a route. Do not retry.

HTTP 503 CAPABILITY_DISABLED
  The key is valid and the route may exist, but the provider/model/credential
  cannot serve the request.
  Action: operator fixes provider configuration. A bounded retry is reasonable
  for transient provider failures only.

## 8. Unauthenticated endpoints

These do not require an app-client key:

- GET /healthz
- GET /readyz
- GET /llm.txt
- GET /llm/{file}.txt

Do not attach the key to public documentation requests if not needed.

## 9. What is not accepted

- Authorization: Bearer <app-client-key> is not the app-client auth mechanism.
- X-Api-Key is not accepted.
- A query parameter named key or api_key is not accepted.
- A Firebase ID token in X-Firebase-Uid is not verified.
- The BACKOFFICE_API_KEY is an operator credential and must never be shipped
  in an application.
